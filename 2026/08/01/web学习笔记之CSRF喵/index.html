web学习笔记之CSRF喵

[TOC]

CSRF？什么好吃的喵

CSRF（Cross-Site-Request Forgery），跨站请求伪造：攻击者诱导受害者访问恶意网站，利用受害者已经在目标网站登录的凭证（即cookie），以受害者的身份向目标网站发送恶意请求

和XSS有点像啊喵…但是还是有区别的（XSS是盗窃密码/执行指令，CSRF是直接借用

CSRF?什么馅的喵？（底层机制）

要理解CSRF，必须先搞清楚浏览器的cookie自动携带机制

在默认情况下，当浏览器向某个域名（比如bank.com）发起HTTP请求时，只要本地存有bank.com的Cookie，无论这个请求是由哪个网站发起的，浏览器都会自动把bank.com的cookie塞进请求头里面

流量对比演示

  1. 正常用户转账（在bank.com网页上点击）

  2. 攻击者诱导转账（受害者在evil.com网页上被诱导）

    evil.com的网页后台执行了一段代码，向bank.com/transfer发起了相同请求，因为目标是bank.com，浏览器会自动附带你的cookie

    bank.com的服务器收到请求，检查cookie：session_id有效，确认是Gloria本人，于是转账成功

CSRF? XSS? 什么区别喵？

XSS（跨站脚本攻击） CSRF（跨站请求伪造）
核心原理 在目标网站注入并执行恶意JS代码 冒充受害者发起HTTP请求
是否需要要盗取cookie 需要（通过document.cookie窃取并发送给黑客） 不需要（利用浏览器的自动携带特性，黑客全程看不到你的cookie）
受害者角色 代码在受害者的浏览器直接运行 受害者不知不觉中充当了“请求转账的工具人”
防御重点 输入过滤、HTML实体转义、HttpOnly标志 CSRF Token、SameSite Cookie属性、Referer校检

CSRF两大经典利用姿势

GET型CSRF（最简单）

如果目标系统的关键操作（如修改密码、发帖、转账）使用的是GET请求

攻击过程： 受害者只要打开evil.com，浏览器在解析<img>标签加载图片时，就会自动向bank.com发起GET请求，并附带cookie，转账在图片加载失败的瞬间已经完成

POST型CSRF（最常用）

如果目标系统使用的是POST请求，攻击者会在恶意页面构造一个隐藏表单，并用JavaScript自动提交

攻击过程： 受害者访问该页面后，用户甚至来不及看清页面内容，JavaScript已经自动提交了表单，借用受害者的cookie完成了跨站POST请求

现代web的三道防线

防御方案A：Anti-CSRF Token（主流方案）

原理：服务器在渲染表单时，随机生成一段无法被攻击者预测的字符串（token），存入session，并在表单中放置隐藏域

校验：提交请求时，服务器校验表单里的Token和Session里的Token是否一致。

由于同源策略（Same-Origin Policy，SOP），恶意网站evil.com无法跨域读取bank.com生成的Token，因此无法构造出合法的请求

这里补充说明一下SOP：怎么才算同源？

协议+域名+端口完全一致

防御方案B：SameSite Cookie属性（现代浏览器利器）

给cookie设置SameSite属性，直接控制跨站请求时是否携带Cookie

  • SameSite=Strict：完全禁止第三方跨站发起请求时携带cookie（最安全但体验较硬）
  • SameSite=Lax：是目前绝大多数浏览器的默认值，允许某些安全的跨站导航（如点击链接）携带Cookie，但禁止POST表单、<img>、<iframe>等跨站请求携带
  • SameSite=None：关闭限制（必须配合Secure属性）

或者彻底不使用cookie，改用Token（如 JWT）

现在的前后端分离架构普遍采用Header传参（Authorization: Bearer Token）

你输入密码登录时，服务器会返回一串加密Token，前端JavaScript把这串Token保存在浏览器的localStorage（本地储存）中，以后每次发请求时，前端必须用JS手动在HTTP请求头（Header）中添加这段Token

防御方案C：校验Referer/Origin请求头

服务器检查HTTP请求头中的Referer或Origin，判断请求是从哪个网站发起的，如果来源不是bank.com本身，直接拒绝

再进行一下补充：HttpOnly

HttpOnly时专门用来给Cookie打的防盗补丁

默认情况下，网页里的JavaScript脚本可以通过document.cookie读取到当前网站的所有cookie

如果网站存在XSS（跨站脚本攻击）漏洞，黑客可以注入一行代码，直接偷走cookie

如果你在服务器给cookie设置了HttpOnly标志：

Set-Cookie: session_id=12345; Path=/; HttpOnly

浏览器会严格锁死这个cookie，阻止任何JavaScript代码读取它，你在控制台敲document.cookie，里面根本看不到这个cookie

🔺🔺注意：HttpOnly并不能防CSRF！

HttpOnly防的是XSS（防止黑客用JS窃取cookie）

而CSRF并不需要窃取cookie，上文已经提到了喵

“在 XSS 面前，CSRF 防御往往形同虚设”

如果黑客先在目标网站找到一个 XSS 漏洞，再利用 XSS 去发 CSRF 请求：

CSRF Token完全失效，因为它依赖于SOP，完全同源

而HttpOnly也不能用，因为即使黑客读取不到cookie，但是可以通过注入恶意JS直接在当前域发起fetch('/transfer')，浏览器会自动把带有HttpOnly的平局塞进这个同源请求的请求头里

因此，在 Web 安全的攻防链条中，XSS 属于最高优先级的执行层漏洞

思路：

一看到“修改邮箱”这种高敏感操作（以及修改密码、转账之类的），只要修改了受害者的邮箱，攻击者就能通过忘记密码重置受害者账号，接管整个账户

正常修改邮箱时，浏览器一般发这样的HTTP请求

看到这个请求包，发现：

  • 请求体里只有一个email参数，没有csrf_token，这意味着请求参数完全可预测且固定
  • 完全依赖cookie认证：服务器只看请求头里带不带合法的session Cookie来判断谁在发请求（这正中CSRF下怀）
  • 缺少SameSite或来源校验：服务器没有配置强校验Origin/Referer，也没有设置SameSite=Strict

所以对于攻击者来说，思路很明确了，我只需要做一个网站，然后诱骗登录了目标网站的人点开，就可以让他的浏览器在后台偷发这个一摸一样的POST请求，让服务器误以为是受害者自己想改邮箱

解释一下这段html

  • <form method="POST" action="...">

    • 干了什么：在页面上定义一个表单，指定目标地址为受害者靶场的真实修改接口。

    • 为什么要这么做：因为浏览器允许 HTML 表单向任意第三方网址提交数据（跨站提交不受同源策略读取限制拦截）。

  • <input type="hidden" name="email" value="...">

    • 干了什么：预先填好要修改的参数名和新邮箱值。

    • 为什么要这么做：

      • name="email" 与接口参数名严格对应。
      • type="hidden" 让页面保持空白无感，防止受害者察觉。
      • value 填攻击者控制的邮箱，一旦成功，账号控制权就转移到了攻击者手中。

  • <script> document.forms[0].submit(); </script>

    • 干了什么：通过 JavaScript 在页面加载完毕的第一时间自动提交表单。

    • 为什么要这么做：

      • 如果不用 JS，页面上就必须放一个按钮“点击修改”，受害者很可能不会去点。
      • 用 JS 自动提交，受害者只要点开链接（或加载网页），浏览器就会在后台毫秒级执行提交动作，达成“零交互”攻击。

这里稍微介绍一下HTML表单

HTML 中的表单本质上是用来收集数据并打包发送给服务器的容器，一个最基础的表单骨架如下：

  • <form>标签：

    • method（提交方式）：最常用就是GET和POST
      • POST：数据放在HTTP请求体（body）中，常用于修改密码、上传、提交敏感数据
      • GET：数据会被拼接到URL后面的查询字符串中，常用于搜索、翻页
    • action(目标路径)：数据要发送到后端的哪一个接口（URL地址）

  • <input>标签：

    • type：表单中的具体字段，通过不同type展示不同形态
      • type="test"：普通的单行文本框，供用户手动输入
      • type="hidden"：隐藏字段，不会显示以爱网页界面上，但提交表单时它的值会鸳鸯发给服务器
    • name：参数键名，后端接口一句这个名称取值
    • value：该参数对应的具体数据内容

  • 提交方式与JavaScript配合：

    • 正常页面通常包含<button type="submit">提交</button>button>供点击
    • 如果通过脚本操作，可以使用document.forms[0].submit()直接调用表单对象的提交方法，浏览器会立即按照表单定义的action和method发起网络请求

test2 Lab: CSRF where token validation depends on request method

思路：

题目看起来是针对csrf进行了一些防御，即使用了 CSRF Token

但是有可能存在请求方法过滤不严的情况，例如后端代码逻辑写成了

开发者认为表单提交默认是POST，只对POST请求开启了Token校验拦截器，但是业务处理函数却支持通过GET查询参数接收数据

因此，当请求方法变为GET的时候，就可以跳过Token校验环节

所以，在遇到此类后端校验逻辑时，构造表单的核心区别就在于method属性的指定

如果目标接口必须以GET方式提交才能绕过检查，表单标签即设为：

浏览器在执行提交时，会自动将表单内的参数转化为URL查询字符串，例如发起：

GET /my-account/change-email?email=目标值 HTTP/1.1

这样发出的请求就转换为了GET格式，避开了仅针对POST的Token校验

完整防御方式：

  • 严格限定接口方法：如果是敏感修改操作，必须在路由成眠严格限定仅允许POST（或PUT）。对所有的GET请求直接返回405，杜绝接口兼容多种方法传参
  • 全局校验防御：CSRF防护应作用于所有可能引发状态变更的操作，而非仅依据HTTP动词进行条件判断
  • 启用SameSite Cookie机制：将关键Session Cookie的SameSite设置为Lax或Strict，从浏览器传输层面限制跨站携带
